# 合併攻擊防作弊與舊版更新流程

> 後續實作狀態（2026-11-28）：共用模型、inputProtocol 1、後端驗算及隔離准入已實作，見 [實作報告](verified-input-report.md)。以下保留前一階段設計與待辦原文；完整舊版更新 UI 與正式發布仍未完成。

日期：2026-11-28（台灣時間）。這是下一階段的具體建議與驗收基準，不是已存在的 API 或正式發布授權。本次僅進場時間限制已接入 runtime；以下新協定／更新 UI 尚未實作。

## 1. 本次已落實的界線

怪物 `approachEndsAt` 是伺服器可信任會話欄位。`serverNow < approachEndsAt` 拒絕新的攻擊；等於時可攻擊；`serverNow >= deadline` 依原規則逾時。前端同一純函式先阻擋預扣血／傷害字／排隊；後端仍獨立驗證，不相信 payload 傳入的時間。沿用500ms攻擊批次、現有收據、傷害及獎勵交易，沒有每擊 Firestore 讀取。

新會話都有明確進場時間。大野狼、老虎及地鼠現有 flightMs=0，因此保持出現即能攻擊；金剛、烈火龍、巨飛鷹、虎頭蜂為10秒、毒牙眼鏡蛇王8秒、遠古巨人7秒。這些數值沒有改變。相容未保存進場時間的歷史會話，不虛構補出一個時間。已完成收據仍可查回，不追溯扣除舊獎勵。

本次沒有重設累計速率的起算點，也沒有調降攻速。既有伺服器額度仍從 startedAt 計算；因此進場等待可能累積 burst 空間，**不能把時間限制當成防止抵達後批次偽造的完整解法**。下一版應把節奏契約與批次驗證一起版本化，避免直接改公式造成玩家合法操作被拒絕。

## 2. 建議採「合法輸入／物理驗算」架構

目標是伺服器驗證一組輸入是否可能產生這些命中；無法證明螢幕前一定是真人。合法機器人輸入仍是殘餘風險。僅加 `hit=true`、可隨意指定的時間或座標、App Check、混淆、隱藏 seed 都不能解決這個問題。

建議保留：

1. 觸控當下本機立即顯示射擊／命中特效與預測 HP。
2. 每約500ms合併輸入；一個原子交易驗證該批並更新會話，不每擊查Firestore。
3. 逾時保留原 batch ID／指紋／順序，查回或重送原批，不產生新攻擊。
4. 伺服器結果校正 HP／序列；勝利獎勵只由已驗證的0HP結算。

### 新協定建議（待實作，名稱未定案）

開戰快照新增獨立的 `inputProtocol`，不可把新語意塞進既有 V4／V5 並沿用同一版號。快照鎖定武器能力、節奏版本、場地座標、怪物運動模型、hitbox版本、開始／進場完成／deadline、damage規則版本。

每批帶 battle/page ID、唯一 batch ID、firstInputSeq、上一個已確認序列、輸入清單。每筆輸入為以下之一：

| 輸入 | 伺服器驗算 |
| --- | --- |
| 近戰按壓 | 正規化座標、當時怪物可受擊狀態、hitbox交集、武器限制及節奏 |
| 弓箭釋放 | 發射原點、拉弓向量、合法速度／重力、箭矢唯一ID、飛行時間與怪物hitbox的掃掠碰撞 |
| 武器模式切換 | 合法裝備槽、按順序重置連爆狀態，不造成傷害、不額外抽爆擊 |

客戶端不直接宣告最終傷害／HP／獎勵或「成功命中幾下」。伺服器依合法輸入推導有效命中，沿用原爆擊與能力快照計算。

### 可沿用的實際來源

- `archery-core.js`：GRAVITY=360；拉弓距離小於12無效；速度為min(1050, distance×9)；`arrowPoint`與`arrowHits`提供彈道／橢圓掃掠碰撞。
- `archery.js`：發射間隔250ms，箭矢最多飛行2.5秒；目前後端卻容許遠程累計10次／秒。兩者不能直接以「後端命中改4次／秒」粗暴對齊，因為不同箭矢的碰撞可能在短時間聚集。下一版應驗證發射時間與同一箭矢僅命中一次。
- `monster-head.js`、各monster Scene／`aerial-patrol.js`：目前存在畫面、動畫、viewport依賴；必須抽出共用的確定性運動／hitbox模型，不能假設現有Phaser像素位置能直接搬進Functions。

### 時間與座標契約

使用固定邏輯場地與正規化座標，前端僅做顯示縮放。不同背景、手機安全區與螢幕旋轉不得改變伺服器合法hitbox。戰鬥中變更viewport要固定既有邏輯場地，或以明確版本化resize事件處理，不能直接信任玩家傳來的hitbox。

輸入時間須單調、在最近已確認的伺服器時間窗口內，限制倒填／未來／亂序與重複箭矢。時間窗口要按實測RTT／抖動定案；本次沒有iPhone行動網路數據，不虛構可接受的毫秒門檻。延遲過大時先確認原批與未提交輸入，不自行再算一次傷害。

近戰節奏與burst也需明確設定，再用真實點擊／掉幀／連發測試確認；本次不直接把原20次／秒改成另一數值。

## 3. 安全與效能驗收

後續至少驗證：正常／低幀率／高延遲、不同螢幕、進場前／exact boundary／過期、跨批命中、多箭同時接觸、偽造座標／速度／時間、重複箭矢、不同裝置同序列、逾時後原批成功、模式切換、不可攻擊類型、HP校正與唯一結算。

必須量測每批讀寫、Functions CPU與延遲，且不能新增每幀／每擊Firestore監聽。建議先建立純模型與測試影子驗算，記錄合法玩家差異但不給新規則額外獎勵；差異為零／可解釋後，才以新的明確白名單協定開放。不能在正式環境默默試算後自動封鎖玩家。

若短期不做伺服器合法輸入模型，維持目前速率型架構就必須明確接受「合法速率的偽造命中可得獎」風險。這是遊戲經濟／安全政策決策；本次不自行解除原NO-GO。

## 4. 舊版更新流程（保留原交易）

### 前提

Service Worker 只快取公開圖片；worker更新不會替換舊頁已載入的JS。新後端須相容舊資料與舊經濟收據；不能先啟用拒絕所有舊版的Rules。舊種別出售／裝備對V2已安全拒絕、V4 client對V5也會拒絕，但現況仍欠完整更新UI。

建議新增的版本能力查詢／錯誤分類，必須明確記成新 API，不能假稱目前已存在。用途是回傳支持的資料／戰鬥／輸入版本、是否需要更新、是否可恢復舊經濟請求。clientBuild只能作相容性提示，不能作防作弊身份證明。

### 狀態流程

`可操作 → 發現版本不相容 → 暫停建立新經濟請求 → 確認原交易 → 顯示更新確認 → 更新並重新載入 → 驗證登入／scope／能力 → 恢復操作`

1. 發現不相容時顯示「遊戲已更新，請先確認未完成交易後重新載入」。不只印Console，不直接清快取或關閉頁面。
2. 確認目前account／group／profile範圍；保留原requestId、原payload與指紋，不將同帳號另一群組的pending帶入此農場。
3. 對已送出的購買、出售、收蛋、偷蛋、清潔、開箱及精煉／解除確認原結果。精煉使用既有結果查詢；其他交易沿用既有原ID、原payload收據重送。無法確認時顯示「結果確認中」，提供同筆重試；不得新建扣款請求。
4. 純戰鬥指令不跨頁重播；依既有abandon/new-page語意作廢原場且不發獎。`homeEncounter collectWhenClear`、`visitEncounter stealWhenClear`含經濟操作，不能因action名稱有Encounter就清除。
5. 結果明確或已保留可恢復pending後，玩家確認更新；保存頁面所在村落及可恢復的UI意圖，不保存可重播的攻擊／獎勵狀態。
6. 更新到固定release內容、重新載入、重新驗證登入與scope，先恢復結果不明的經濟收據，再開放新操作。已完成結果的UI只顯示一次，不重新發獎。
7. 兩分頁／裝置的版本提示可用BroadcastChannel作UX同步，但後端頁面／scope／收據驗證才是安全邊界。
8. 離線時可以提示需要網路才能確認原結果；不能用Cache API回應來假裝交易成功，也不能為完成更新而刪除未知版本pending。

### 緊急暫停與回退

先停止新的精煉／解除或新協定准入，保留既得能力、V2資產、舊寶箱及原收據查詢。舊版不相容V2/V5時不能直接回退舊前端／後端。優先向前修復／更新流程，不整批還原資料或將武器全部退回+0。

## 5. 執行順序與尚待確認

建議順序：本次進場限制隔離驗收 → 新輸入協定的場地／時間／節奏契約 → 純物理模型與批次驗算 → 舊版更新協調器／介面 → 真實手機及網路影子比較 → 重新Step A審查。

本次已確認應保留「即時本機特效＋合併提交＋伺服器最終結算」，不改成每下等網路。尚待產品／實測定案：各武器節奏契約、RTT容忍窗口、可接受的自動化操作風險、受支援最低client artifact及更新UI文案。未定案項目不以任意常數實作，也不擅自調降獎勵或提高怪物HP。

### 已開舊分頁無法被「新API」自動升級

真正的舊頁面沒有新版本查詢／訊息監聽器，因此只新增API或改worker並不能讓它憑空出現更新視窗。發佈需先供應相容更新橋接版，仍未載入橋接版的舊頁面只靠後端安全拒絕與清楚的手動重新載入訊息；不能宣稱已能自動更新所有舊頁面。

新能力只對已完成新頁面／協定握手的操作開放；未確認版本的頁面不應建立新的精煉付費意圖，但原已完成經濟收據仍需可確認。另一裝置日後回來仍要重新握手。這不需要假裝能盤點所有休眠舊裝置。

未來正式前端應以不可變release路徑／完整module graph內容hash發布，不能只對main.js加query卻讓子模組繼續使用舊HTTP快取。先驗證所有子模組版本一致，再開付費功能；錯版本時停在更新／確認交易畫面，不初始化半套Phaser Scene。以上建置與橋接流程尚未實作。

# 02－影響分析、安全風險與經濟資料缺口

來源：`0233ffd632d82ac0cede326d508718ea3cdbe734`，2026-11-27。`DEVELOPMENT_RULES.md` 尚未取得，核對待補；本文件不授權實作。

## 1. 變更邊界

本階段不新增精煉功能、個體集合、材料、正式 Rules／Index，也不修改既有測試讓它們變綠。以下全部是未來影響與待確認方案。實際回歸結果見 [04](04-regression-baseline.md)。

| 模組 | 個體化影響 | 必須保護的原功能 |
|---|---|---|
| 商品目錄 | 種類仍是商品；買入後建立多個個體 | 價格、未開賣狀態、容量與扣款規則不被前端竄改 |
| 商店出售 | 指名 Instance ID，可選多把，不能只減種類 quantity | 不賣已裝備個體；不擅自變更賣價或偷偷退款；賣出分類仍只雞／武器／其他 |
| 倉庫 | 同款分開圖示、+N、獨立詳情與分頁 | 非武器數量、寶箱分類、容量與已有租約不受影響 |
| 裝備 | 種類 ID 改為可解析的近戰／弓個體 ID | 空近戰有木棒回退；弓可卸下；種類限制沿用 |
| 戰鬥 | 入場查個體、凍結加成／版本，之後按索引重算 | 九種怪物、原時限、±10、1.5 倍爆擊、500ms 合併命中不增加逐擊 RPC |
| 禮包 | `domain.award` 不能再只回傳 farm，需要可交易化的個體發放計畫 | 既有 accountId 名額與原請求去重，不能跨群組多領 |
| 寶箱 | open/openMany 同時交付個體／材料及個體 ID | 舊內容快照、20 箱、原戰利品、容量不足不部分扣箱 |
| 每日 | 目前只有金幣，未來材料需新獎勵快照／發放接點 | group/account 隔離、午夜邊界、一天領一次與事件 +1 |
| 排行榜 | 加強武器會間接增加討伐效率 | 只計原成功擊退事件一次，不把精煉成功算擊退，不改本期週期或排序 |
| 圖鑑 | 目前未開放完整入口／里程碑發獎，僅可規劃接點 | 不把尚未存在的獎勵當成已接線；與現有說明圖鑑分開 |
| 管理中心 | 新增版本化精煉模組與查詢 | 保留 admin 當前 claim 驗證、expectedRevision、reason 與稽核 |
| 存檔／鏡像 | farm 只留必要相容投影，私有個體／成本帳本分開 | 不擴大公開村落讀到的資料，不造成每次 farm 快照包含全部歷史 |
| PWA／舊分頁 | 需要伺服器 schema／protocol gate，不只是前端旗標 | 舊分頁不得用舊 buy/sell/equip API 改新個體資產 |

## 2. 安全基準及風險登錄

P0：任何正式切換前必須解決；P1：功能開放前必須定義／驗證。這些是靜態發現或測試限制，不代表已在正式環境成功利用。

| ID | 等級 | 現況證據 | 影響／建議 |
|---|---|---|---|
| GOV-01 | P0 | 指定 DEVELOPMENT_RULES 文件不存在於本機／main | 無法宣稱符合它；請補文件再核對，不自行發明規則 |
| SEC-01 | P0 | 完整規則檔是 candidate；root firebase.json 未指定 Rules | 正式 release 未驗證；先唯讀匯出、比對，不能部署片段 |
| SEC-02 | P0 | group user 子集合有泛用 write allow | 新個體放該處可能可被本人直接偽造；使用 ops 私有 namespace 或完整收窄所有 OR 路徑 |
| SEC-03 | P0 | legacy 前端直寫源碼仍存在；正常開關 true 選後端 | 強制新 Rules／所有後端 writer gate；不能只改／隱藏前端按鈕 |
| DATA-01 | P0 | 只有數量與裝備種類，且木棒沒有數量 | 不能直接對同款全部套一個精煉等級；先個體化及驗證 |
| DATA-02 | P0 | buyWeapon／domain.award／chests.open 都可發武器 | 任何遺漏來源都會再產生舊資料；統一發放規劃，舊區域也更新 |
| DATA-03 | P0 | 每物品發放可達 1,000、寶箱一次 20 箱 | 每把一文件可能超出交易上限；大批發放須分批票據／容量預留，不丟棄既有箱內容 |
| ECON-01 | P1 | 正式金幣、材料產出資料未提供 | 不根據測試 Alice／Bob 或對話舊人數估玩家持有量 |
| COMBAT-01 | P1 | V4 才是 1.5 倍；舊版本另有 2～3 倍分支 | 若有新小數協定，必須新增明確分支與協商；不能只把版本改 5 |
| COMBAT-02 | P1 | 現有 seed 提供前端，可預測序列 | 不重用它抽精煉；後端驗算不是完整反外掛 |
| VER-01 | P1 | 當前戰鬥設定每次新會話生效 | 凍結武器原始能力會改變全體調整語意；須先確認版本／補償政策 |
| MIRROR-01 | P1 | mirror.farm 複製整份 farm；有公開村落讀取 | 私有成本、意圖與抽樣不可放入 farm；RTDB 關讀取不等於後端未鏡像 |
| COMPAT-01 | P0 | SW 只更新美術，舊分頁 JS 可繼續活著 | 改旗標／清快取不足以防舊 writer；新舊 API 必須按 farm schema 拒絕或相容 |
| TEST-01 | P0 | 本機 Emulator JAR 下載 403 | 真實 Rules／Auth／Firestore 並行交易基準未完成；不能用 MemoryDB 通過替代 |
| LIMIT-01 | P1 | save-core 部分數量只驗證有限且非負 | 移轉前額外要求安全整數、合法裝備、來源唯一；異常停住人工確認 |

既有候選 fallback 規則有 2026-12-16 期限；只影響該 fallback 覆蓋的模組，不應說整個農場都在那天停機。期限稽核另案處理，不在本階段修改。

## 3. 金幣與資源的完整寫入者清單

除了 `gameOpsFarmTransaction`，至少還要盤點／接線：

- `gameOpsRedeem → service.redeem → domain.award`。
- `gameOpsDailyChallenges → daily-challenges.handle`。
- `gameOpsAdmin → management.mutate('adjustPlayerCoins')`。
- `chests.open/openMany`、戰鬥及歡迎信獎勵，在既有 farm transaction 中交付。
- 保留的 legacy UI 分支與舊 `js/farmgame.js`；它們必須由正式 Rules 擋住，不可靠刪檔當安全邊界。

不同區域、分頁、管理 API 和獎勵來源可能同時更新同一 farm。移轉不能從舊快照把整份 farm 蓋回去，也不能只對 shop action 加鎖卻讓禮包／箱子持續加舊武器數量。

## 4. 經濟資料可得性：未讀正式資料

已存在 `createReporting.capture/report` 與管理員報表入口，但本次沒有提供已授權的營運統計匯出或唯讀管理連線。沒有使用 ADC 猜測身份、掃描正式玩家，也沒有把測試資料當營運數據。

| 要求 | 目前可用的程式來源 | 缺口與下一步 |
|---|---|---|
| 金幣中位數、P90、P95 | report 可回 currentCoins | 未取得正式結果。以 group＋account 為農場單位、排除損壞值；明列是否僅活躍農場；n=0 不產生分位數 |
| 活躍玩家每日產出／消耗 | ops_farm_report_events metrics.coinsAdded/Spent/Net | report 是每次已提交餘額變化的正負淨額，不是完整來源分類帳；需活躍定義、每日來源事件、覆蓋起點及去重 |
| 武器持有量／使用率 | farm 各武器數量與 equippedWeapon/Bow | 沒有歷史持有／使用分鐘；目前快照可算持有率與裝備率，不能說歷史使用率。木棒是隱含，須按回退邏輯計 |
| 各怪物每日擊敗 | report.metrics.monsters、verified events | 只涵蓋開始記錄後區間；Results 列表會截斷，不能掃現有陣列還原全部歷史 |
| 寶箱取得／開啟 | boxes.droppedAt/status/openedAt/result | 目前 report 無完整寶箱日統計，chestCount 僅未開數，不代表歷史取得；需按唯一 box ID 計或增量聚合 |
| 任務完成率 | daily_days.progress/tasks、claimedAt、daily_grants | 完成率不等於領取率；daily 文件按需建立，不能用「有開過任務視窗的人」冒充全部活躍分母 |

建議固定台灣日界 `[00:00, 次日00:00)`，存 UTC 時間；農場與全域帳號統計分開。分位數方法可採 nearest-rank，文件化樣本範圍／n／缺失率；不同日期或方法不得直接混比。

可先使用既有報表做一次經授權的聚合匯出，去識別化後提供：日期、活躍農場數、餘額分位、金幣各來源／支出、武器持有／裝備數、怪物擊退、箱子取得／開啟、任務 eligible/completed/claimed。無資料的日期標 unknown，不補 0。

## 5. 僅依需求表的理論經濟（不是營運結果）

沿用前一則確認中的需求：+9 攻擊累計 +50%，兩種率各 +15 個百分點、無保底。成功率 100/90/80/70/60/50/40/20/10%；費用 1000/2000/3000/4000/5000/5000/5000/5000/5000；石頭 1/1/1/1/2/2/2/3/3。

| 指標 | 數學結果 |
|---|---:|
| 全部一次成功 | 35,000 金幣、16 石 |
| 無保底平均嘗試 | 約 25.96 次 |
| 無保底平均總成本 | 約 118,519.84 金幣、62.12 石 |
| 解除：只按成功成本退 30%／50% | 本表不變時 10,500 金幣、8 石 |
| +8→+9 連敗 10 次／20 次機率 | 約 34.87%／12.16% |

不能以平均值承諾任何玩家保證價格。依預設兩種率 5%→20%，長期同模式穩態爆擊約 5.25%→23.81%；再乘攻擊 1.5 倍，平均輸出約 +63.6%，不是僅 +50%，也不是每場精確擊殺時間。

程式預設七天簽到總計 1,600、任務 6,200。若只有這些收入且全勤、不支出，118,519.84 約相當於 15.2 週；這僅作程式預設比較，不是實際玩家的養成天數。

正式平衡至少要先有 14～28 天可靠資料，並確認石頭是否占容量、目標 +9 天數、同時養幾把武器、重複解除的資源回收及失敗後流失。Phase 1 不發布掉落率、不調金幣，也不擅自啟用保底。

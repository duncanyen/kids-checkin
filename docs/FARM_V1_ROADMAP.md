# 咕咕村落 V1.0 修復與營運路線圖

> 日期：2026-11-09（Asia/Taipei）；基準 main `3849615e6e49696b0e9dfb6bd7b469301c43a883`。這是下一階段規劃，不是已新增功能，不授權本次正式部署／改資料。風險編號參照 [安全報告](FARM_SECURITY_AUDIT.md)。

## 1. 實作原則與可執行順序

先建立可驗證的權限與資料基線，再逐條遷移交易；不是把瀏覽器送來的價格、勝負或亂數原封搬進 callable。每個工作以小型獨立 PR、Emulator 測試與相容策略交付；必要的資料清理先出 dry-run 報告，不重設玩家資產／排行榜。

建議順序：

1. **R01 現行完整 Rules／索引／資料基線 → R02 身分橋接與公開資料邊界。** R01 的蒐集及測試可立即開始；未取得 Rules 前，其他純服務可獨立開發，但不能宣稱整體已安全。
2. **R03a 優先交易：升級、買藥、擴倉、一般物品出售 → R03b 其餘買賣／養殖／倉庫／歡迎禮。** 先封已重現參數缺口，再收斂全部經濟寫入；一般物品假售價亦不可遺漏。
3. **R04 可信任遭遇與結算 → R05 偷蛋／防守／排行事件。** 共享 R03 的資料驗證、時間、operationId 與帳本，不建立另一套資產更新器。
4. **R06 Rules 最終收斂＋整合／部署 manifest＋備份還原。** 在 staging 驗證舊客戶端相容與新端點，再另行申請正式部署；禁止直接封鎖仍在用的全部欄位。
5. **R07–R10 營運 P1 → R11–R13 效能 P2。** 真機與必要監控是正式關卡，不可因放在後段就免驗。

最先修復的五項工作包為 **R01、R02、R03a、R04、R05**。R03b／R06 同樣是 V1 正式經濟可信度的 P0 閘門，不能只做前五項就宣稱可發布。

## 2. P0：正式經濟／競賽前必須完成

### R01　完整權限與資料基線（F01、F06、F07、F09）

- **交付**：由擁有者提供現行完整 Firestore Rules／完整索引與版本、Auth／Hosting／Functions 入口；建立不含憑證的 schema 與 caller→path→field 權限矩陣。將正式 rules snapshot 與待修改 proposal 分開，不能把片段當完整現況。
- **實作**：Emulator fixtures 涵蓋 owner／他人／公開跨村／閉村／退群／停用／admin browser；對每個 broad allow 列出重疊路徑。盤點舊 js/farmgame.js、phaser-farm.js 是否有可達入口及寫入。
- **驗收**：文件列出所有 farm／farmMail／通知／ops 的 create/read/update/delete；明確測試直接增資產、改租約、整份覆蓋與 delete。取得現行規則也許先會暴露允許案例，需如實記 fail，而非刪測試。
- **相依／限制**：需正式配置資訊，但本工作可唯讀蒐集，仍不得擅自部署或匯出玩家秘密資料。

### R02　身分橋接與公開資料邊界（F05、F06）

- **交付**：photoSession／liveSession 帳號＋IP 限流與退避、維持現有通用驗證失敗回應、濫用安全紀錄；玩家 Auth 漸進遷移 ADR；公開 profile／村落摘要的 proposed schema／API。
- **實作**：先以測試帳號驗證舊登入相容，避免將密碼／PIN 放在公開 users 文件的長期設計。依舊客戶端依賴規劃分段遷移，不任意更改 accountId、users ID 或 group members。若拆集合，先獨立資料遷移設計與回復方案。
- **驗收**：連續／跨 IP 猜測被限制，合法登入可恢復；profile payload 不含任何憑證／內部狀態；停用／移除／換群組正確拒絕；管理 claim 仍只由可信任環境設定。
- **政策**：保留管理員 MFA／App Check 選用；若要改為必要需另行決策與 Console 驗證，不能用它替代伺服器授權。

### R03a　優先商品交易（F02、F08）

- **交付**：提議的 farm action API（命名待設計）支援 upgradeCoop、buyMedicine、expandWarehouse、sellItem 一般道具交易。API 只收 action／商品識別／正整數 qty／固定 requestId，不接受客戶端價格或完整 farm。
- **實作**：後端共用商品規則、伺服器查價、safe integer 上下限、當前等級、餘額與容量；同筆記錄 farm patch、成功 operation receipt 及必要經濟紀錄；前端處理未知結果重試。
- **驗收**：本次 F02 四個交易重現全部拒絕；負數、零、分數、超限、假價、過期設定、相同／不同 payload 共用 id、兩分頁、提交成功回應遺失均有明確結果。非法操作不扣款、不新增／減少庫存，不建立成功收據。
- **發布相依**：R01 權限矩陣與新舊 client 最低版本策略；先測後端，再切前端與相應 Rules，不可讓未更新 client 無預警壞掉。

### R03b　其餘經濟與養殖收斂（F01、F08、F14）

- **範圍**：四雞買賣、蛋及道具出售、武器買賣、收蛋、產量補算／生病死亡、餵食、治療、丟棄、裝備、放風、歡迎禮及清潔；所有能改經濟或影響產能的入口納入。
- **實作**：後端沿用 poultry／inventory／housing／combat 純規則，now／亂數由可信任層提供；正常動畫可預覽，但結果以後端回應為準。跨自家／拜訪的產量及病程一致。
- **驗收**：原價／產蛋／每日待收容量／健康優先售雞／已產蛋保留／最低放風／裝備不可出售／病雞治療及歡迎禮規則不變；倉庫滿、斷線、並行與舊存檔相容皆通過。發獎或購買後的 hensState／readyEggs／摘要一致。
- **資料策略**：可疑歷史資產只先標記與對帳報告；不在遷移中批次歸零或用預設值覆寫。

### R04　戰鬥的可信任狀態機（F03、F08）

- **交付**：所有怪物的 encounter claim→active→settled／expired 持久狀態、固定 id 與不可重播收據；用同一種截止／重入語意覆蓋舊 Boss 與地鼠類。
- **實作**：後端決定資格、互斥、開始／截止、敵人與裝備合法性。定義可驗證命中協議與頻率上限，避免只收任意 win 或總傷害。畫面動畫與後端狀態分離，必要檢查批次提交降低延遲，但不能省掉可信任驗證。
- **驗收**：零命中／不合法武器不能獲獎；伺服器時間到期一律依既有規則扣款；重整／雙分頁／重入／斷線不能重置時限或逃避已開始遭遇。超過歷史 32／128 筆後重送舊 id 也不得再發獎。獎勵、損失與狀態同筆。
- **產品相容**：保留目前各武器命中數、怪物時限／門檻／掉落／滿倉保證掉落行為，若改規則另提案，不藉安全遷移調平衡。

### R05　偷蛋、防守及排行榜可信任事件（F04、F11）

- **交付**：可信任 steal attempt、server RNG／now、完整跨村資格與來源／目標交易、伺服器活動計數及榜單查詢。
- **實作**：同筆讀雙方農場與群組，驗證對象、雙方公開、冷卻、容量、待收蛋、護衛犬有效租約；固定 attemptId 鎖定亂數結果及通知識別。分數由成功事件派生，不能提交 score 增量。
- **驗收**：固定 Math.random、改時鐘、偽造組別／owner、閉村／退群與到期同時發生仍正確；一次成功只減目標一蛋、增來源一蛋及本期一分，防守成功不給分，重送不重擲。當期以 `[startAt,endAt)` 伺服器時間記錄。
- **排行**：保留歷史欄位與賽季，不重設全玩家原累積。定義跨群組同帳號分開計分的既有政策；若要更改計分單位，先提出產品決策。

### R06　P0 整合閘門與經濟恢復（F07、F09、F10）

- **交付**：正式 Rules 合併 proposal、demo／staging 整合測試、所有啟用查詢的索引矩陣、發布 manifest、備份／還原演練證據及回滾 runbook。
- **驗收**：經濟／guardDogs／ops 不可由一般 client 或 admin browser 直寫；owner delete 受控；合法仍保留的 client 更新可用。真實交易並發搶額、拒絕、回滾與重試通過，不以 MemoryDB 取代。
- **備份**：擁有者核定 RPO／RTO／保留與成本，還原到隔離專案後通過資產及收據對帳；不只 restore farm，亦包含相關 claims／計數／收據／必要身分關聯。
- **版本**：先建立相容後端與 requiredVersion／能力回應策略，再切 client 與 Rules；規則收緊前確認舊 client 不會持續把整個 farm 覆寫回舊格式。正式部署另獲授權並留證。

## 3. P1：高優先營運與穩定性

| 工作 | 交付內容 | 驗收條件 |
| --- | --- | --- |
| R07　稽核與濫用觀測（F12） | 將經濟操作、管理成功／失敗、安全拒絕、限流、補發分層記錄；統一 correlationId；最小化資訊與保留政策 | 可追查單筆操作而不輸出憑證；故障可告警且去重；Auth／role 拒絕也有適當安全事件，不把未授權 payload 全存入稽核 |
| R08　活動封榜／頒獎（F11） | 伺服器結束時間、分數快照、人工審核／異常標記、winner／award 收據；活動碼與禮包對應檢查 | 重啟／重送不重頒，過期分數不進榜；停用／額滿／錯碼不宣稱必可兌換；未定頒獎流程前公告不承諾自動發獎 |
| R09　真機與弱網（F09、F13） | iPhone Safari／主畫面、iPad 直橫向、Android，前背景、系統暫停、切網／斷線／重連及多分頁測試表 | 留裝置／OS／版本／步驟／影片與錯誤；輸入鎖釋放、場景返回、交易未知結果及存檔不丟失；至少 15–30 分鐘基線，與無頭測試分開 |
| R10　存檔及事件恢復工具（F03、F10） | 唯讀存檔診斷、Schema／摘要一致性檢查、可重試補償提案與審核介面 | 損壞存檔不重建覆蓋；可疑資產與缺收據先列差異；人工確認的修復有前後差異、原因、唯一識別及備份，禁止自由輸入整份 farm |

## 4. P2：後續規模與維護優化

| 工作 | 內容 | 驗收條件 |
| --- | --- | --- |
| R11　排名與公開讀取投影 | server top-N、分頁與公開摘要；限制每次跨村 fan-out | 10／100／1000 玩家測量讀取、延遲、大小與費用；不再為榜單下載完整 farm／users；閉村與停用同步可追蹤 |
| R12　負載與資料容量 | 評估 hensState、結果陣列、通知、單禮包／限流桶的競爭與熱點 | 具體寫入率與延遲／錯誤率門檻；load test 不影響正式玩家，收據清理策略不能破壞防重播 |
| R13　素材與版本治理 | Atlas／引擎 CDN、快取、載入 retry、舊入口退場與文件／指標一致性 | 不破壞漸進載入、場景清理或圖像尺寸；桌面與平板實測，動態後端設定不與編譯常數互相覆蓋；每版可定位 schema／code hash |

## 5. 每個工作包共同完成條件

- 有來源與資料路徑範圍、錯誤與未知結果處理、跨群組／停用／版本／重送測試。
- 正常規則與既有存檔的回歸未被改成迎合測試；新增容量例外／經濟變更需另列產品決策。
- 前端、Functions、Rules 與索引相容性逐一記錄；沒有使用正式玩家資料當測試 fixture。
- 公開文件不含密碼、PIN、token 或私鑰，操作紀錄也不存未過濾完整 payload。
- PR 說明包含測試證據與尚未驗證事項；部署另依 [發布清單](FARM_RELEASE_CHECKLIST.md)，無自動視為已獲正式部署授權。
